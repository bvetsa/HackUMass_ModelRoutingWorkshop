## A tiny Python primer

| You see | It means |
| --- | --- |
| <code>prompt = "Hello"</code> | Store text under the name prompt |
| <code># explanation</code> | A comment; Python skips it |
| <code>from module import Name</code> | Bring a definition from another file |
| <code>function(value)</code> | Call a function with an input |
| <code>return value</code> | Stop the function and give its result to the caller |
| <code>if condition:</code> | Run the indented block only when true |
| <code>class RuleRouter:</code> | Define an object type with settings and methods |
| <code>router = RuleRouter()</code> | Create one such object |
| <code>router.route(request)</code> | Call its route method with a request |
| <code>decision.model</code> | Read the model field on a decision object |
| <code>self</code> | The current object inside a method |
| <code>None</code> | No value, such as no classifier score |

| <code>{"small": function}</code> | A dictionary mapping a key to a value |
| <code>[first, second]</code> | A list containing two values |

Indentation groups statements. Request and Decision are names defined by this
project, not Python keywords.

## 1. Start at start.py

[start.py](../start.py) runs from top to bottom:

1. Import Request and RuleRouter from routing_workshop/routers.py.
2. Store a prompt string.
3. Construct a Request containing that string.
4. Construct a RuleRouter with the default 180-character cutoff.
5. Call router.route(request).
6. Receive a Decision and print its fields.

The route call temporarily leaves start.py:

~~~text
prompt -> Request -> RuleRouter.route()
                       check keyword
                       check length
                       otherwise choose small
       <- Decision(model, reason, score)
print the fields
~~~

No answer is generated in this first example.

## 2. Follow RuleRouter in routers.py

Open [routers.py](../routing_workshop/routers.py).

Request and Decision are dataclasses: small containers whose constructors are
generated by Python. Request holds prompt. Decision holds model, reason and
optional score. A type hint such as prompt: str describes the intended value;
__post_init__ performs actual checks. frozen=True prevents later field changes;
slots=True limits the object's allowed attributes.

RuleRouter.__init__ stores max_chars on self. RuleRouter.route then:

1. Lowercases the prompt so capitalization does not affect the keyword test.
2. Checks for a complexity keyword. A match returns large immediately.
3. Otherwise checks whether prompt length exceeds max_chars.
4. Otherwise returns small.

The r"..." expression is a regular expression, a text-matching pattern. Word
boundaries keep "prove" from matching "improved". Quotes do not protect a
keyword: "Translate the word prove into French." still triggers this crude
rule. That is an intentional failure to investigate.

The original email prompt has no keyword and is short. The final return
produces Decision("small", "short prompt without trigger").

## 3. Compare a learned decision

Run and open [scripts/compare_routers.py](../scripts/compare_routers.py):

~~~sh
python3 -m scripts.compare_routers
~~~

The function main() contains the example. The final
if __name__ == "__main__": main() runs it when launched as a program.
Importing the file's definitions does not run main().

The script loads synthetic_cases.json through read_data(), which resolves
files inside routing_workshop/data/. Each case is a dictionary. It collects
ONLY split == "train" cases into (prompt, needs_large) pairs.

Here is a smaller illustration than the script's 32 bundled training examples:

~~~python
from routing_workshop.routers import LocalRouter, Request

training = [("extract email", False), ("prove theorem", True)]
local = LocalRouter(training, threshold=0.6)
decision = local.route(Request("prove theorem"))
print(decision.model, decision.score)
~~~

False labels the authored small class; True labels large. Labels here are
teaching choices, not measured model capabilities.

Follow LocalRouter.__init__:

- Tokenize prompts into lowercase word/number pieces.
- Count words separately for each class.
- Count examples per class and collect the vocabulary, the known words.

Follow LocalRouter.score:

1. Keep words seen in training. Return None if none are known.
2. Compute each class prior: its fraction of training examples.
3. Estimate word probability in that class:
   (word count + 1) / (total words in class + vocabulary size).
4. Combine word evidence with the prior using logarithms.
5. Convert the two log scores to a large-class posterior between zero and one.

For the two-example illustration, both priors are 1/2 and vocabulary size is
four. For "prove theorem", each word has probability 2/6 in the large class
and 1/6 in the small class. Combining both words gives large posterior 0.8.
This estimates the authored routing class, not answer correctness.

Follow LocalRouter.route:

- Score None -> choose large with an unknown-word fallback reason.
- Score within 0.05 of threshold -> choose large with an ambiguity reason.
- Otherwise choose large at/above threshold, small below it.

The default threshold is 0.6. Because of the ambiguity band, a score just below
0.6 may still select large. These costlier defaults guarantee neither safety
nor answer quality.

## 4. Connect a decision to an answer function

A router chooses; a backend supplies an answer/outcome.

Read [integration.py](../routing_workshop/integration.py). route_and_call():

~~~text
Request(prompt) -> router.route(request)
                -> backends[decision.model](prompt)
                -> return decision and answer
~~~

The dictionary maps small/large to ordinary functions. Only the selected
function runs. Missing roles and non-text returns are errors. Backend failures
propagate; there are no hidden retries or extra calls.

Run and read [the integration example](../scripts/integration_example.py):

~~~sh
python3 -m scripts.integration_example
~~~

Its small_backend() and large_backend() functions look up historical text.
It uses an exact bundled prompt and labels output OFFLINE RECORDED RESPONSE
ONLY. It is a working lookup, not new inference. Arbitrary prompts fail.

## 5. Understand the two outcome sources

[backends.py](../routing_workshop/backends.py) contains:

| Backend | Response | Evaluation quality |
| --- | --- | --- |
| SyntheticBackend | Designed PASS/FAIL placeholder | Designed pass outcome |
| RecordedBackend | Exact historical text | Human pairwise preference credit |

A seed makes synthetic outcomes repeatable. Hashing seed + prompt + role gives
the same result regardless of policy order. Success probabilities are authored.
RecordedBackend verifies hashes and reconstructs response/vote pairs from
selected source rows. A miss never silently becomes synthetic.

Outcome holds response, quality and assumed resources. Routers see only
Request(prompt). The simulator is black-box from that interface; the teaching
assumptions remain public code. Verification checks dataset consistency, not
answer truth or authentication of historical execution.

## 6. Read benchmarking last

Start at run_benchmark() in [benchmark.py](../routing_workshop/benchmark.py).
Its numbered phases:

1. Load the same evaluation set/backend for every policy.
2. Build five policies; train the classifier from training examples only.
3. Warm up every policy once.
4. Shuffle policy/question order and time repeated local calls.
5. Keep quality once per unique question, not once per timing repeat.
6. Compare against always-large on the same questions.
7. Attach evidence labels, environment and data hashes.

TimingSample names each repetition's fields. Router time is selection alone;
local dispatch includes selection and backend lookup. Modeled end-to-end adds
assumed service time to measured dispatch. No artificial sleep or model
inference is measured.

Read [BENCHMARKING.md](BENCHMARKING.md) for metrics/uncertainty, and
[DATA.md](DATA.md) for provenance.
